> **היציאה תוקנה. הניקוי לא בוצע — ובכוונה.** הניקוי המקומי חייב לרוץ **אחרי**
> שבונה המטען המתוקן נמצא בפרודקשן. הוא אינו שם: הענף הזה הוא PR ולא מוזג
> (C.8). הרצת הניקוי עכשיו הייתה יוצרת בדיוק את המצב הגרוע ביותר שהאפיון מזהיר
> ממנו — הממשק אומר "ללא הגבלה" בזמן ש-Beds24 ממשיך לאכוף 31.

בסיס: `docs/MAXSTAY_NO_LIMIT_SPEC.md` (נמדד חי 2026-07-25). ענף `feat/maxstay-no-limit`
מעל `main = 43f0d32`.

## מה תוקן

### 1. שכבת היציאה — הליבה

`src/lib/channel/beds24-room-ceilings.ts` (חדש) קורא את `maxStay` **ברמת החדר**
מ-`GET /properties?includeAllRooms=true`, לכל חדר בנפרד, ושומר ב-cache ל-6 שעות.
בונה המטען שולח את הערך הזה כשהערך המקומי הוא NULL:

```ts
// beds24-ari-payloads.ts
maxStay: c && c.maxStay != null ? c.maxStay : m.maxStayCeiling,
```

**למה התקרה ולא 3650.** שניהם מגיעים לאותה תוצאה אצל Beds24, אבל 3650 מחזיר
warning בכל דחיפה, ו-`inspectEnvelope` מסמן **כל** מערך `warnings` כ-`partial`.
כל דחיפה מסחרית הייתה נקראת חלקית לנצח והאזהרות האמיתיות היו נטבעות ברעש.
שליחת התקרה עצמה מחזירה 201 נקי — נבדק בשומר (אסרשן 5).

**למה לא קבוע 365.** כל 15 החדרים מחזיקים 365 היום, אבל חדר שתקרתו תשתנה בפאנל
יישבר בשקט. הערך נקרא מהספק, לכל חדר בנפרד. השומר מוכיח את זה עם חדר שתקרתו 200
(אסרשן 4).

**fail-open.** תקרה שלא ניתן לקרוא ⇒ אין ערך ⇒ השדה מושמט — בדיוק ההתנהגות
הקודמת. תקלה אצל הספק לעולם לא תחסום דחיפה מסחרית, ולעולם לא תמציא תקרה: תקרה
מומצאת כותבת הגבלה **אמיתית** על ליסטינג חי (אסרשן 7).

### 2. ולידציה — `.min(1)` בשני שדות

`src/lib/validation/rates.ts`. `0` אינו הגבלה חלשה יותר אלא **חזקה יותר**:
Beds24 מהדק אותו ל-**לילה אחד**, ובמסלול שלנו הוא מפיל את **כל** הבקשה
(`beds24-ari-payloads.ts` דוחה ערך שהייה מתחת ל-1). `price = 0` סוגר חדר בשקט
דרך `blocked = price1 <= 0`. `rate-plans.ts` תמיד דרש `.min(1)` — הקובץ הזה היה
היוצא מן הכלל.

### 3. ברירת המחדל בטופס

`GroupUpdatePanel.tsx` — `useState(7)` ⟶ `useState(NO_LIMIT)`, סנטינל `NO_LIMIT = 0`
שנכתב **NULL** ולא 0, ותווית "ללא הגבלה". **זה המנגנון שילד את ה-31:** מפעיל
שמדליק את השדה ולוחץ "החל" מטביע מספר שלא ביקש על כל הטווח.

**הערה על הענף `fix/quote-window-long-stay` (LOS, לא ממוזג):** הוא מחזיק גרסה
משלו של הסנטינל והצ'יפ. הענף לא נגע (חוק concurrency). בעת ה-rebase שלו יהיה
חפיפה בקובץ הזה — וגם **התנגשות מספר מיגרציה**: הוא מביא `055_length_of_stay_discounts.sql`
בזמן ש-main כבר מחזיק `055_booking_com_channel_reports.sql`. הוא יצטרך 057.

### 4. השומר — `check:beds24-maxstay-no-limit`

מריץ את הניקוז **האמיתי** מול DB בדיקות משלו, מאחורי מוק **מצבי** שמממש את החוזה
שנמדד: שומר ערך לכל (חדר, תאריך), מהדק לתחום `[1, תקרה]`, ו — העיקר — מתייחס
ל-`maxStay` חסר/null כאל **no-op** שמשאיר את הערך הקודם. כל אסרשן קורא את המצב
הזה בחזרה, ולכן מודד **התנהגות** ולא צורת מטען.

הוא **אינו** פונה ל-Beds24. שומר שכותב לליסטינג החי בכל הרצה הוא כתיבה מסחרית
אמיתית בלי דרך חזרה; המדידה מקודדת במוק — אותה בחירה בדיוק ש-`check:beds24-ari-drain`
עושה לשאר חוזה הלוח.

| | תוצאה |
|---|---|
| 7 אסרשנות | ✅ ירוק |
| **A** — `src/` נקי של `43f0d32` (אימות זהות: 0 שורות הפרש) | 🔴 **אדום התנהגותי** — `enforcing [31,31,31,31,31,31]`. לא שגיאת import: השומר משחזר את הבאג בפרודקשן |
| **B2(a)** — ענף ה-NULL חוזר ל-`null`, כל המבנה נשאר (מודול, קריאה, cache, שדה, הפניה, אותו מספר בקשות) | 🔴 אדום |
| **B2(b)** — התקרה מוקשחת ל-365 במקום להיקרא מהספק | 🔴 אדום |

### 5. `check:beds24-ari-drain` הורחב — והתחזק

השומר הקיים דרש שהניקוז ידבר **נקודת קצה אחת**, ולכן ה-`GET /properties` החדש
הפיל אותו. החוזה אכן התרחב, והתיקון הישר הוא לנקוב בנקודה השנייה ולא לרכך:
מותרת, GET בלבד, אותו header, ו**אסרשן 11 סופר את הקריאות על פני כל הניקוזים
בריצה ונכשל מעל אחת**. B2: ניטרול כתיבת ה-cache בלבד (Map, TTL, lookup, expiry
נשארים) מאדים אותו ב-8 קריאות.

**עלות הקרדיטים — החישוב:** אחרי האיפוס כל הערכים זהים, ולכן הדחיסה מכווצת את
כל האופק ל-**19 טווחים**. `CALENDAR_ENTRIES_PER_REQUEST = 100`, ולכן

(תקרת הריצה 73 בקשות, תקרת הטווחים 500 מול ~15 שייווצרו). **אין צורך בפיצול לפי אופק.**

### החסם, במפורש

האפיון קובע סדר מחייב: **קודם בונה המטען, אחר כך הניקוי**. בונה המטען המתוקן
נמצא בענף הזה בלבד — פרודקשן רץ על `43f0d32`, שעדיין משמיט את השדה. אילו הניקוי
היה רץ עכשיו:

1. 4,830 השורות היו הופכות ל-NULL מקומית,
2. הטווחים היו מתלכלכים והניקוז **הפרודקשני** היה **משמיט** את `maxStay`,
3. Beds24 היה ממשיך לאכוף 31 — **לנצח**, כי אין פעולת מחיקה,
4. והממשק היה מראה "ללא הגבלה". פער שקט שאף מסך אינו מסוגל להראות.

**הניקוי ממתין למיזוג הענף הזה ולדפלוי.** אחריו הוא פעולה אחת על מלוא האופק.
